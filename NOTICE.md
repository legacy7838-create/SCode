# ZCode Feature Description and Third-Party Component Notice

This notice applies to the source code and build artifacts published from this repository. Each runtime form has different features, permissions, storage locations, and network behavior; the default settings of one form should not be understood as the uniform settings of the entire project.

## I. AI Output, Execution Permissions, and Automation Risks

AI-generated code, commands, explanations, files, and suggestions may contain errors, omissions, security defects, or third-party rights issues. Verify against actual files, command exit statuses, tool results, and tests; a model claiming "completed", "safely handled", or "authorized" does not constitute proof of fact or authorization. Before important operations, review the execution target, recipients, and impact, and maintain recoverable backups.

Files, terminal, Git, Agent tools, and external processes can read/write files, start processes, and access the network within the operating system account permissions in which they actually run. In Web or remote workspaces, operations may occur on the server side, SSH host or container environment; the execution location cannot be determined solely by the device hosting the current page. The current shared Agent execution adapter does not provide a default OS sandbox; working directory, workspace identity, Git worktree, browser page isolation, and Node REPL runtime context should not be treated as system-wide isolation guarantees for all tools.

The shared runtime configuration defaults to the `build` permission mode; the standalone CLI executing non-interactive tasks via `--prompt` uses `yolo` when `--mode` is not specified. Interactive sessions, desktop sessions, resumed tasks, and hosts can use their respective configured, saved, or passed modes. Whether per-operation confirmation is required depends on tool declarations, permission rules, and runtime mode; `yolo` without read-only planning constraints enabled allows normal tool operations, while interactive tools and tools explicitly requiring confirmation still have their own rules. Model tool approval is not a unified permission switch for the entire application; it cannot be assumed that terminal operations, plugin processes, or update downloads all go through the same approval process. See [CLI Prompt Modes](apps/zcode-cli/packages/cli/src/run.ts#L486) and [Tool Permission Judgment](apps/zcode-cli/packages/core/src/permission/service.ts#L97) for details.

## III. Local Data, Logs, and Credentials

Data may be stored separately on the desktop device, browser, CLI host, SSH environment, and external services. Desktop and server-side data directories may be affected by the runtime environment and startup configuration, and include settings, sessions, attachments, caches, task records, plugins, and logs; the standalone CLI's default session database is at `~/.zcode/cli/db/db.sqlite`. Closing a window, logging out, uninstalling the client, or deleting a workspace should not be understood as having cleared all copies in other environments, independent data directories, backups, and external services.

The defaults and entry points for the memory feature differ: the standalone CLI's default configuration enables memory, while the desktop app settings default to off. When enabled, saved sessions can be analyzed, memories persisted, and reused in subsequent tasks; related extraction or organization may generate additional model requests. Automated plans, run records, and unfinished tasks also have their own persistence locations; restoring these records does not guarantee that prior external operations were undone or can be fully replayed.

The shared Agent's model input/output logs are written locally by default in both development and production runs, except in the test environment. Logs may contain prompts, code, context, tool parameters, and model replies; request headers and some image/video data have desensitization, but it cannot be assumed that all user text has been desensitized. Production defaults have rotation and trimming; explicitly enabling full retention changes this behavior. The desktop main process, Host, scheduler, Web service, and remote daemon each have their own logs and crash records; a single log size cap does not represent a project-wide uniform retention period.

Credential storage mechanisms also differ: the CLI shared credential file uses an encryption mechanism, with the default key derivable from local environment information, and the read logic also accepts plaintext records; desktop/Node service credentials also use local encrypted files with configurable or environment-derived keys, not the system keychain; Web OAuth credentials may be stored in localStorage. Model configuration, environment variables, plugin/MCP settings, SSH configuration, and remotely synced data may also contain valid credentials; these stores should not be uniformly treated as system keychain, hardware isolation, or "never leaves this machine" guarantees.

The embedded browser uses persistent browsing data; explicitly importing cookies and LocalStorage from other browsers can give it the corresponding login state. Clearing cache and clearing all site data are different operations; browser records, downloaded files, web recordings, and model logs are not necessarily deleted by the same cleanup entry. Do not write real keys or tokens into version-control-tracked files. Before copying logs, uploading feedback, sharing conversations, or backing up data directories, check the receiving scope to avoid committing real credentials, raw sessions, and private project content to public repositories or issue reports.
